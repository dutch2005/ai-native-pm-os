# How to update the spec

← [Home](Home.md)

## Rule of thumb

**If you change an architectural fact, update the spec. If you change content, you don't.**

| Change | Update `ai-native-pm-os.speq`? | Why |
|---|---|---|
| Add a new lesson to module 7 | No | Lesson files are content under `COURSE_CONTENT.OWNS`. The structure is the same. |
| Add a new module (e.g., module 11) | Yes | Module count is structural; lesson order needs updating in `AGENTS.md` and `CLAUDE.md` too. |
| Rename `CLAUDE-OUTPUTS/` to something else | Yes | `VOCABULARY ClaudeOutputs` and the LAYER `OWNS`/`NEVER` rules need to follow. |
| Add a new MCP connector lesson | Maybe | Content-only is no, but if it introduces a new secret kind, add it to `SECRETS`. |
| Add a new course mode (e.g., `instructor`) | Yes | Extends `course_mode.outputs ALWAYS matches-active-mode`. |
| Tighten or relax a contract (e.g., allow auto-complete in test mode) | Yes — and bump version, mark `BREAKING` in CHANGELOG | Breaking changes invalidate previously generated artifacts. |
| Fix a typo in a lesson | No | Pure content. |
| Reword the agent's tone guidance | No | That lives in `AGENTS.md` / `CLAUDE.md`. The spec doesn't constrain tone. |
| Add a new field that should never be logged | Yes | Add to `CLASSIFY` as `credential` or `pii`, and to `OBSERVABILITY must-not-log`. |
| Change `progress.json` schema | Yes | The spec implicitly assumes the current shape. If you change it, document the migration in CHANGELOG. |

## The workflow

```bash
# 1. Edit the spec.
edit ai-native-pm-os.speq

# 2. Validate before committing.
speq check ai-native-pm-os.speq

# 3. If validation passes, also re-check that AGENTS.md, CLAUDE.md, and GEMINI.md
#    still match. Vocabulary and contract restatements live in those files too.

# 4. Run the lesson parity check if you added/renamed/removed a lesson.
bash scripts/check-lesson-parity.sh

# 5. Bump CHANGELOG inside the spec. Use BREAKING / ADDED / CHANGED / DEPRECATED.

# 6. Commit. The state file (state_ai-native-pm-os.speq) is gitignored.
git add ai-native-pm-os.speq AGENTS.md CLAUDE.md GEMINI.md
git commit -m "spec: <what changed>"
```

CI runs steps 2 and 4 automatically on every PR via [`.github/workflows/validate.yml`](../.github/workflows/validate.yml). If your edits don't pass `speq check` or break lesson parity, the PR will fail CI before review. There's also a weekly [`vocabulary-drift.yml`](../.github/workflows/vocabulary-drift.yml) workflow that scans lesson markdown for forbidden synonyms — manually triggerable with `gh workflow run vocabulary-drift.yml` if you want to audit before opening a PR.

## Installing the speq CLI

```bash
npm install -g @speq-ai/speq
speq --version  # should print 0.2.x or later
```

If you don't have Node.js, you can still use the spec — it's plain UTF-8 and any agent can read it. The CLI just gives you syntactic validation and state tracking.

## Common validation errors and fixes

| Error | Cause | Fix |
|---|---|---|
| `FLOW '<name>' step N references undeclared entity '<x>'` | Flow step uses `<x>.action` but `<x>` isn't in `ENTITY` | Either add `<x>` to `ENTITY`, or rephrase the step using an existing entity |
| `VOCABULARY entry must be PascalCase` | Used snake_case or camelCase | Convert to PascalCase |
| `LAYERS name must be UPPER_CASE` | Used PascalCase or lowercase | Convert to UPPER_CASE |
| `CALLS references undeclared layer` | Layer name typo or layer not yet declared | Check spelling; ensure all layer names match |
| `At most one layer may declare BOUNDARY external` | Two layers both have `BOUNDARY external` | Pick one — the single untrusted entry point |
| `A field classified credential must not appear in must-log` | OBSERVABILITY block accidentally lists a credential field as must-log | Move it to must-not-log, or change the classification |

## When something seems wrong with the spec itself

Per the SpeQ skill:

- State precisely what you observed (e.g., "FLOW capstone_graduation step 1 references `module-10-prereqs` which isn't an entity").
- Do **not** modify the spec to make it consistent with code you already wrote.
- Do **not** invent new entities or layers to paper over the gap.
- Ask the project owner what the right answer is.

The spec is the source of truth. Code that contradicts it is wrong; the spec is right by definition until the owner decides otherwise.

## What about `state_ai-native-pm-os.speq`?

It's generated by `speq check` on first run. It tracks per-entity build status (`PENDING`, `PARTIAL`, `BUILT`) and per-check status (`UNVERIFIED`, `OK`, `FAILED`). It is **not committed** — `.gitignore` excludes `state_*.speq`.

Each contributor regenerates it locally. Don't share state files between machines or environments.
